# #14 회원 온보딩 구현 계획

`feat/14-onboarding`에서 카카오·구글 로그인으로 생성된 회원이 3단계 입력을 제출하고 가입을 완료하도록 한다. 정책은 [결정 이력](history.md), HTTP 계약은 [API 합의](api.md)를 기준으로 한다. Java 21, Spring Boot, PostgreSQL, Flyway, 기존 Bearer 인증을 사용한다.

## 배포 전 결정

현재 배포 스크립트는 앱 교체 실패 시 동일한 DB에서 이전 이미지를 실행한다. 이전 이미지는 Hibernate 스키마 검증을 실행하므로 기존 `users` 컬럼을 제거하면 이전 이미지 기동이 실패할 수 있다. 사용자는 이번 배포 DB에 보존할 데이터가 없다고 확인했다. 데이터 백업·복원 검증을 이번 배포의 선행 조건으로 두지 않는다.

사용자가 #14에서 Java 필드와 DB 컬럼을 함께 정리하도록 승인했다. 기존 Flyway 이력을 보존하고 새 마이그레이션에 컬럼 제거를 포함한다. 배포 복구 제약은 Q17 이력에 남긴다.

## 권장 커밋 순서

아래 목록은 구현 전 작업 순서다. 실행 결과는 [진행 상황](progress.md#구현-및-검증-결과)에 기록했다.

### 1. `feat: 시도와 자치구 조회 API 추가`

- [ ] Flyway에 시·도·자치구 테이블과 서울 25개 구 시드를 추가하고, 시·도·자치구 공식 코드의 유일성 및 소속 FK를 검증한다.
- [ ] `/api/v1/cities`와 `/api/v1/cities/{cityCode}/areas`를 연결한다. 테스트에서 `11`의 목록이 중복 없이 25개이고 `11440`이 포함되는지 확인한다.

### 2. `feat: 회원 온보딩 완료와 닉네임 확인 추가`

- [ ] `User`, `UserRepository`, `UserService`, `UserController`, `UserResponse`를 중심으로 온보딩 입력과 저장을 연결한다. 완전한 요청만 `ACTIVE`로 전환하며 프로필·선호·지역 저장은 한 트랜잭션에서 처리한다.
- [ ] `GET /api/v1/users/nickname-availability`에서 본인 기본 닉네임은 사용할 수 있게 하고, 타인의 대소문자 변형은 충돌로 판정한다. 최종 저장에서도 기존 유니크 제약을 사용한다.
- [ ] `4.0+`가 왕복하는지, 필수값 누락과 동성만·혼합복식 조합 및 지역 4개가 거절되는지 확인한다. 검증 또는 저장 실패 후 상태가 `ONBOARDING`인지, 같은 입력은 재제출 시 성공하고 변경 입력은 `409`인지 확인한다.
- [ ] 기존 `ExperiencePeriod`와 매치 생성용 `MatchType`의 값이 온보딩 선택지와 다르므로 코드 매핑 및 기존 저장값 호환성을 확인한다. 매치 생성·조회 테스트로 회귀를 점검한다.

### 3. `feat: 소셜 표시 이름을 본인 정보에 제공`

- [ ] 카카오·구글 OAuth 매퍼, `SocialIdentity`, `UserRegistrationService`, `SocialAccount`를 연결한다. 본인 정보와 온보딩 완료의 공통 응답에서 `socialDisplayName`을 제공한다.
- [ ] 두 공급자의 이름 제공·누락을 확인한다. 가입 대기·완료의 본인 응답에 저장값이 포함되고, 이름이 없으면 `null`인지 확인한다. 기존 로그인과 검증 이메일 중복 가입 방지도 다시 확인한다.

### 4. `feat: 프로필 사진 업로드 조회 삭제 추가`

- [ ] 파일 키를 저장하는 회원 스키마와 Docker 볼륨 기반 저장소를 연결한다. 업로드·조회·삭제 API와 Compose 볼륨은 같은 커밋에 둔다.
- [ ] 가입 대기 회원의 업로드·삭제, 다른 로그인 회원의 Bearer 조회, 비로그인 조회 거절, JPEG·PNG와 5MB 제한, 실패 시 기존 사진 유지, 삭제 후 `null`을 확인한다. 앱 컨테이너 교체 후 사진이 유지되는지 확인한다.
